### 2. Router (`lib/chatbot/router.ts:1-25`)

- Iterates `intents` in registration order, filters by `roles.includes(session.role)`, keeps the intent with strictly-highest score (`score > highestScore`) — ties go to whichever intent appears first in the array.
- Zero-score fallback (`router.ts:21-24`): `` `That's a strong place to start. You said: "${message}" — what would make that feel like a win this week?` ``, `intentId: "fallback"`. No card, no `suggestedChips` set here — downstream `route.ts:18` backfills the **full role menu** (`??=`), not a targeted best-guess.
- This is exactly the Phase 6 confidence-scoring rework from `fitbot-capability-expansion` (`plan.md` Decision 8, `match-scoring.ts`) — deterministic regex-only, satisfying the "pass for AI through deterministic code" constraint.

- `route.ts:34` (GET/history reload) **unconditionally overwrites every historical assistant message's `suggestedChips` with the full role menu** — original per-turn contextual chips are lost on reload.

### 7. CSS/animation conventions (`app/globals.css`)

- Existing keyframes: `chat-pulse` (opacity+translateY, typing dots), `shimmer` (skeleton loading), `fade-up` / `scale-in` (entrance transitions, paired with `.animate-*` utility classes), `booking-confirmed` (success pop).
- Convention: purpose-named `.animate-*` utility classes paired with each keyframe; short durations (0.18s–1.4s); custom easing tokens `var(--ease-out)`/`var(--ease-spring)`.

## Inferences

- **High confidence:** the mixed match-scoring styles (`Number(regex.test())` vs. the shared helpers) aren't a functional bug today, but represent inconsistent adherence to the Phase 6 pattern — these intents currently can't out-score a same-scoring competitor via entity match since they have none.
- **Medium confidence:** "spin the MomentumArc while thinking" is only currently visible on the transient typing-indicator row's avatar, since real message avatars never coincide with `isSending === true` (the assistant message only appears after the response lands).
- **Medium confidence:** the fallback's coach-like tone is a deliberate soft redirect — replacing it with a suggestions UI is tone-compatible, not a contradiction of existing design intent.

## Unknowns

- Whether `fitbot-deterministic-upgrade` was formally approved/executed or abandoned in favor of `fitbot-capability-expansion` — matters for avoiding duplicate/contradictory decisions.
- Whether `search_members_by_attributes`/`list_members_for_staff`/`search_members` RPCs already select `membership_status`/`phone`/`birthdate`/`staff_notes` at the SQL level, or would need a migration to expose them.

## Risks

- `who-is-booked.ts` has an explicit comment: raw `bookings` row counts don't reliably reflect seed data (`booked_count` is the source of truth). Any new roster-naming intent/chip that queries `bookings` directly will hit this same gap.
- Router tie-breaking is strict "first registered wins" — new intents need deliberate placement; broadening existing intents' entity coverage risks new collisions resolved only by array order.
- `route.ts:18`'s `??=` backfill silently defaults to the full role menu if a handler (including any new fallback-suggestions path) forgets to set a narrower `suggestedChips` — the new fallback path in `router.ts` must explicitly set targeted chips or it'll render the generic menu, defeating the point.
- `route.ts:34` (GET/history) unconditionally overwrites historical `suggestedChips` with the full menu on every reload — any feature relying on persisted contextual chips will lose that context on reload today.
- The blanket reduced-motion rule collapses `animation-iteration-count` to 1 — a spin animation needs a defined, acceptable frozen end-state for reduced-motion users.
